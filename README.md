# Playbook Use Case Design Framework

A design-first framework for security automation planning and workflow development.

The framework is inspired by Palantir's [Alerting and Detection Strategy (ADS) framework](https://github.com/palantir/alerting-detection-strategy-framework). Where ADS imposes structure on *detection* engineering, this framework does the same for *automation* engineering of SOAR workflows and subflows.

## Why

Palantir built ADS because, in their own words, alert development lacked *"rigor around the creation, development, and implementation [...]"* which led to noisy, poorly-documented detections and analyst fatigue. 

As for me, I found the same problem when developing workflows in my preferred SIEM and SOAR platform: Google SecOps. I found out that the *automation that gets built ad hoc, undocumented, poorly planned, and untested tends to be brittle, hard to hand off, and expensive to fix when something upstream changes.* I've seen the consequences of poor workflow engineering in my own automation workflows and in the workflows of other peers and community users, which often converge in me having to adapt, re-design, and re-deploy the automation workflow from the ground up.

Thus, I decided to create this framework. It helps (me), the automation engineer, to ask a set of questions *before*, *during*, and *after* engineering an automation workflow. The result is a **Use Case Design Document (UCDD)** that records every aspect needed to plan and design a workflow effectively, and to share with your teammates and other people in the community.

## Core principles

The UCDD template exists to put **pressure** on four design principles and best practices into every automation workflow use case.

* **Modularity** — automation should be built as **reusable subflows** (blocks), not monolithic workflows, so a fix or update to shared logic propagates to everything that depends on it. Modularity also solves the spaghettification of automated workflows.
* **Resiliency** — workflows should **anticipate failure**. Automated actions like API calls should have explicit error handling rather than assuming the *"happy path"*. 
* **Short-circuiting principle** — workflows should take the **cheapest path to a correct outcome** whenever one exists to reduce MTTR, free up resources quickly for the next workflow in queue, and minimize processing time. For example, skipping re-enrichment of an already-enriched entity or checking an allow-list before running an expensive lookup. 
* **Parameterization** — workflows should be **portable** across environments through parameter configuration rather than workflow modification or adaptation. While it is true that each organization has its own challenges, parameterizing workflows and subflows can make a once one-environment tied workflow portable to many environments at once.

## Terms

| Term | Definition |
|---|---|
| **SOAR** (SOAR Platform) | SOAR stands for **Security Orchestration, Automation, and Response**; the category of security platform this framework designs automation for (e.g. Google SecOps SOAR, Cortex XSOAR). |
| **Workflow** (playbook, automation workflow) | Refers to the automation logic being designed. A workflow is a composition of a trigger condition, and automation logic in the form of integration actions, which executes to reach an outcome. Most SOAR platforms call this a playbook. |
| **Subflow** (block) | A reusable, self-contained piece of a workflow with its own input/output conditions or parameters, usually invoked by a main workflow through chaining (the subflow is placed in-line in the automation workflow) or attachment (the subflow is executed by invocation of an integration action). |
| **Modular Workflow** | A workflow built from subflows rather than as a single monolithic workflow, so a fix or update to shared logic propagates to everything that depends on it. It is the direct expression of the *Modularity* principle above. |
| **Workflow Trigger** | The condition that needs to be met by an alert to execute an automation workflow. Depending on your SOAR Platform capabilities, triggers can be executed via webhooks or by conditions that check whether an alert meets the criteria (e.g. Trigger a workflow if the alert was generated by X product). |
| **Integration** | A SOAR platform's connection to an external product or service (e.g. an EDR, an email system, a Threat Intel Platform, etc.), exposing that product's capabilities as actions a workflow can call. |
| **Action** | A single, discrete operation a workflow performs through an integration (e.g. send an email, enrich an indicator, close a case). Actions often require configuration either through the integration or in the action itself (e.g. Action to send an email will need to know the SMTP server and the recipient of the message). |
| **Workflow Priority** | The tier assigned to a workflow's trigger to resolve collisions when more than one workflow's trigger matches the same alert (see `UCDD-FRAMEWORK.md` Section 3's 1-2-3 priority model). |
| **MTTR** | Mean Time To Resolve/Respond — the metric the Short-circuiting principle above is optimizing for by taking the cheapest correct path through a workflow. |
| **UCDD** | Use Case Design Document — the artifact this framework produces: the record of a workflow's objective, categorization, trigger, strategy, implementation, assumptions, error handling, simulation, and resources (see `UCDD-FRAMEWORK.md`). |
